Master Build Spec

Madar OS — New Developer Operational Spec G

هذا هو المستند التنفيذي الأعلى للمبرمج. هدفه أن يشرح Madar كنظام تشغيل تعليمي وتجاري متكامل من أول دخول المستخدم حتى إقفال الدورة التشغيلية والمالية والأرشيفية، مع تضمين Room OS بالتفصيل الكامل داخل نفس المستند، بحيث لا يبقى فراغ منطقي أو تقني أو تشغيلي يحتاج سؤالاً إضافياً قبل التنفيذ.

هذه النسخة G تجمع منطق المستند التشغيلي الأساسي، وتوسعة النسخة F الخاصة بالغرفة، وتحوّلها إلى blueprint واحد يغطي: الهوية، الصلاحيات، الحجز، الموافقة، الدفع، الجلسة، التسجيل، الأرشفة، القيود المالية، مستحقات المعلم، طوابير الإدارة، الربط مع مزودات البث والوسائط، متطلبات الأمان، الكيانات، الحالات، الخدمات، الأحداث، وتسلسل البناء المرحلي.

1) المبادئ الحاكمة

1.1 طبيعة المنتج

Madar ليس Prototype صفحات ولا مجموعة شاشات منفصلة، بل نظام تشغيل موحّد يربط ثلاث طبقات: Entry OS، Room OS، Admin/Finance OS. أي نجاح شكلي في الواجهة لا يُعتد به إذا لم تعمل السلسلة كاملة من الدخول حتى الإقفال المالي.

  • كل شاشة يجب أن تخدم إجراءً حقيقياً.
  • كل حدث مهم يجب أن يخلّف state change وaudit trail.
  • الحقيقة التشغيلية لا تُقرأ من الواجهة بل من الحالات والقيود والسجلات.

1.2 تعريف النجاح

  • الطالب يستطيع الدخول، الموافقة، الدفع، الحجز، والانضمام للحصة في الوقت الصحيح.
  • المعلم يستطيع تفعيل ملفه، إدارة جدوله، تشغيل الحصة، وإنهاءها مع احتساب مستحقه تلقائياً بعد completion.
  • الإدارة تستطيع المراجعة، اعتماد المعلمين، متابعة النزاعات، تجهيز التحويلات الشهرية، واعتماد شيت التحويل يدوياً الآن.
  • الأرشيف، التسجيل، والمال مرتبطون بنفس session lineage ولا يوجد انفصال بينهم.

4) الدورة التشغيلية المغلقة

User Entry → Identity Check → Role Routing → Catalog/Availability → Booking Intent → Consent/Pay Gate → Invoice/Transaction → Booking Confirmed → Join Token Ready → Room Open → Live Session → Recording/Artifacts → Session End → Completion Evaluation → Teacher Payable → Wallet Ledger Posting → Monthly Payout Sheet → Manual Admin Approval of Transfer Sheet → Payout Marked Paid → Monthly Revenue Remainder / P&L / Audit Closure

هذا التسلسل ليس وصفاً عاماً، بل هو العمود الفقري الذي يجب أن تنبني عليه الجداول، الحالات، الخدمات، والأحداث. أي قطع في هذه السلسلة يعني أن Madar لم يُبنَ كنظام تشغيل متكامل.

5) دورة الطالب

5.1 الدخول والتهيئة

  • يدخل الطالب عبر OAuth أو واتساب/هاتف مع OTP.
  • إذا كان جديداً يمر بـ onboarding مختصر: الاسم، الصف، المواد المهتم بها، ولي الأمر عند الحاجة، سجل الموافقة القانونية.
  • بعد التحقق يتم توليد جلسة مصادقة آمنة قصيرة العمر مع refresh policy واضحة وربط single active token عند الحاجة.

5.2 الحجز

نوع الحجزالمنطقالحالة الناتجة
Groupالطالب يختار صفاً + مادة + offering منشور + موعد محدد وسعر ظاهرConfirmed مباشرة بعد نجاح الدفع أو تفعيل المجانية حسب القاعدة
Privateالطالب يختار معلماً ووقتاً متاحاً ويرسل طلباًPending Teacher Confirmation ثم Confirmed بعد قبول المعلم وسداد الالتزام المالي

5.3 بوابة الموافقة والدفع

  • قبل اكتمال الحجز يجب حفظ Consent Record إذا كانت السياسة تتطلبها.
  • يُنشأ Invoice لكل التزام مالي، ثم Payment Transaction عند محاولة الدفع.
  • نجاح webhook من بوابة الدفع هو المصدر المعتمد لتثبيت التحصيل وليس مجرد رسالة الواجهة.
  • لا يُنشأ JoinAccessToken صالح إلا بعد صلاحية الحجز للدخول.

5.4 دخول الجلسة

  • زر الدخول يتفعل ضمن نافذة زمنية configurable قبل بداية الحصة.
  • عند الدخول يُسجّل SessionAttendance مع وقت الدخول والجهاز وعنوان IP والسياسات المرتبطة.
  • إذا لم يحضر الطالب أو خرج مبكراً تطبق Policy Engine قواعد no-show أو partial attendance أو الاسترداد.

6) دورة المعلم

6.1 التفعيل

  • المعلم يملأ TeacherProfile: المواد، الصفوف، أنماط التدريس، الأسعار، التوفر، بيانات السحب، الهوية.
  • لا يصبح مرئياً للحجز حتى يتحول status إلى Active بقرار إداري أو rule-based activation.

6.2 الجدول

  • يرى اليوم، الغد، الطلبات المعلقة، الجلسات التي تحتاج مراجعة، والرصيد والمستحقات.
  • في الخصوصي يقبل أو يرفض ضمن SLA زمني، وفي المجموعات ينشر الفتحات الجاهزة.

6.3 أثناء الحصة

  • يفتح الجلسة، يشغّل الكاميرا/المايك، يدير السطح الرئيسي، يسمح لطالب محدد بالتفاعل، وينهي الجلسة.
  • يبدأ التسجيل تلقائياً بحسب الإعداد المعتمد، ولا يعتمد النظام على زر يدوي وحده لحفظ الجلسة.

6.4 بعد الحصة

  • تُقيّم الجلسة: completed / disputed / no-show / cancelled.
  • إذا أصبحت completed وبحسب القواعد، ينشأ TeacherPayable وتُرحّل قيوده إلى WalletLedger.
  • المعلم يرى مستحقاته المتراكمة ويقدّم PayoutRequest عند تحقق شروط السحب.

7) دورة الإدارة والمال

7.1 الطوابير

7.2 الإقفال المالي

  • بعد كل جلسة مكتملة: إنشاء payable + posting إلى ledger + revenue entry حسب القاعدة المحاسبية المعتمدة.
  • آخر الشهر: النظام يُنتج Monthly Teacher Payout Summary وشيت تحويل مجمّع لكل معلم مؤهل.
  • في المرحلة الحالية: تحويل مرتبات المعلمين ليس آلياً بالكامل؛ بل يُجهَّز الشيت ويُعتمد يدوياً من الإدارة ثم تُعلَّم التحويلات Paid داخل النظام.
  • في مرحلة لاحقة: يمكن تفعيل تنفيذ شبه آلي أو بضغطة زر، لكن بعد استقرار دورة الاعتماد اليدوي.
  • النظام يجب أن يحسب أيضاً باقي المبلغ المحصل من الطلبة بعد خصم مستحقات المعلمين والاستردادات وأي تسويات، مع إظهار Revenue Remainder وP&L snapshot وتقارير open balances.

8) Room OS الكامل

Room OS في G ليس ملحقاً بصرياً، بل جزء عضوي من الدورة التشغيلية. الغرفة هي المكان الذي تتحول فيه booking المؤكدة إلى session فعلية، والتسجيل إلى archive، والحضور إلى completion، والجلسة المكتملة إلى payable.

8.1 مبادئ الغرفة

  • الغرفة تفتح فقط للجلسات المؤهلة.
  • السطح الأساسي هو Shared Lesson Surface: PDF / Screen Share / Content Stage.
  • السبورة موجودة كأداة قوية، لكنها ليست محور المنصة إلا عند الحاجة التعليمية.
  • كل ما يحدث داخل الغرفة يجب أن يكون قابلاً للبث والتسجيل والأرشفة ضمن نفس session lineage.

8.2 منطق فتح الغرفة

الحدثالشرطالناتج

8.3 طبقات الواجهة داخل الغرفة

8.4 السطح الرئيسي

  • الافتراضي عند بدء الحصة: lesson PDF أو shared content إذا كان مرفوعاً مسبقاً.
  • يدعم annotation بالقلم، التحديد، النص، pointer، التكبير، والتنقل بين الصفحات.
  • يمكن للمعلم الانتقال إلى screen share أو media display أو board mode دون كسر البث أو التسجيل.

8.5 Board Mode الثانوية ولكن الكاملة

  • Multi-page whiteboard وليست صفحة واحدة فقط.
  • Templates للصفحات: سطور عربي، سطور إنجليزي، مربعات رياضيات، شبكات رسم، صفحات تدريب منظّمة.
  • إمكانية التنقل بين الصفحات، إضافة صفحة جديدة، نسخ صفحة، ومسح صفحة مع تأكيد مناسب.
  • جميع صفحات السبورة تدخل ضمن نفس التسجيل والجلسة ويمكن حفظها كـ session artifacts.

8.6 تفاعل الطالب داخل الغرفة

  • الأصل أن الطالب يشاهد ويستمع ويتابع.
  • الكتابة أو الحل على السطح المشترك لا تتم إلا بعد منح explicit permission من المعلم لطالب محدد أو مجموعة محددة.
  • يمكن أن يرى الطالب مؤشر الدور الحالي: viewer / invited to solve / active writer / muted.

8.7 التحفيز التعليمي للأطفال

  • طبقة Child Engagement اختيارية حسب نوع الحصة والفئة العمرية، وليست مفروضة على حصص الكبار.
  • عند الإجابة الصحيحة يمكن تشغيل applause sound أو celebratory balloons/effects على الشاشة.
  • عند الخطأ يمكن تشغيل تنبيه أخف بصرياً أو صوتياً دون إحراج أو إزعاج.
  • هذه التأثيرات يجب أن تكون قابلة للتفعيل والإيقاف من إعداد الحصة أو إعداد المعلم.

8.8 الأدوات المساعدة

  • آلة حاسبة حديثة داخل الغرفة كأداة utility مدمجة.
  • رفع ملفات مساندة وصور عند الحاجة التعليمية.
  • قائمة المشاركين، الشات، والحضور في لوحة جانبية لا تزاحم المسرح الرئيسي.

8.9 التسجيل والأرشفة

  • التسجيل يبدأ تلقائياً مع live start بحسب السياسة.
  • عند انتهاء الحصة تُغلق live input وتبدأ pipeline الأرشفة ورفع الأصل أو الناتج إلى مزود الأرشيف.
  • كل recording asset يرتبط بـ session_id وscope وصلاحيات المشاهدة.
  • archive availability لا تعني public access؛ بل وصولاً مقيّداً وموقعاً حسب الصلاحيات.

8.10 الحماية

  • Dynamic watermark user-bound وsession-bound على البث أو المشاهدة.
  • Focus/visibility change detection مع logs قابلة للمراجعة.
  • Short-lived signed URLs للوسائط والتسجيلات.
  • المتصفح لا يضمن منع تسجيل الشاشة بالكامل؛ التصميم المطلوب هو deterrence + traceability + policy enforcement.

9) البنية التقنية المقترحة

9.1 الواجهة

  • Clean HTML/JS أو framework خفيف منضبط، دون تضخم غير مبرر.
  • واجهات منفصلة منطقياً: Entry, Student, Teacher, Admin, Room.
  • Stage-first design في الغرفة وqueue-first design في الإدارة.

9.2 الخلفية

  • Services modular واضحة boundaries.
  • REST/HTTP APIs + webhooks + workers + event bus أو event dispatcher.
  • Policy engine للحضور والاسترداد والأهلية المالية.

9.3 مزودات الوسائط

  • البث الحي منخفض الكمون: Cloudflare Stream Live / WebRTC أو مزود مكافئ.
  • الأرشفة وإعادة المشاهدة: Bunny Stream أو HLS archive layer مع Signed URLs.
  • يجب بناء Media Adapter abstraction حتى لا يرتبط التطبيق مباشرة بمزود واحد على مستوى منطق الأعمال.

9.4 بيئة التشغيل

  • VPS نظيف، Ubuntu LTS، Nginx reverse proxy، HTTPS، PM2 أو manager مماثل.
  • فصل أسرار البيئة، مفاتيح مزودات الدفع، مفاتيح الوسائط، ومفاتيح التوقيع عن الكود.

draft → submitted → under_review → approved → paid / rejected / held

15) متطلبات API والواجهات

  • واجهات مصادقة، ملفات، كتالوج، توافر، حجوزات، دفع، webhooks، room lifecycle، attendance، media، wallet، payouts، admin queues.
  • كل endpoint يجب أن يطبق role-based access + resource-level authorization.
  • واجهات room يجب أن تدعم lifecycle واضحاً: prepare, open, join, grant-interaction, end, archive-status.
  • واجهات المال يجب أن تمنع أي تعديل مباشر للأرصدة خارج ledger transaction model.

16) الأمن والامتثال

  • جلسات مصادقة آمنة قصيرة العمر وsingle-session policy عند الحاجة.
  • RLS أو ما يعادلها على مستوى البيانات الحساسة.
  • Rate limiting على auth وOTP والدفع والنقاط الحساسة.
  • Masking للبيانات الحساسة في السجلات.
  • Audit logs غير قابلة للحذف من الواجهة.
  • Signed URLs للوسائط والأرشيف.
  • Dynamic watermark على البث والتسجيل.
  • فصل مفاتيح المزودات، سرية webhook signatures، والتحقق من سلامة requests.

18) سيناريوهات القبول النهائية

  1. طالب جديد يدخل، يوافق، يدفع، يحجز مجموعة، يدخل الحصة، تُسجل الجلسة، تُؤرشف، ويظهر أثرها المالي كاملاً.
  2. طالب يحجز خصوصي، يقبل المعلم، ينجح الدفع، يتفعل join token، تفتح الغرفة، ينهي المعلم الجلسة، ويُنشأ payable صحيح.
  3. المعلم يكمل ملفه، يُعتمد، ينشر فتحة، يدير الحصة باستخدام PDF/board/tools، ثم يرى payable في محفظته.
  4. الإدارة تراجع نزاع جلسة وتجمّد payable لحين القرار، ثم تُطلقه أو تلغيه حسب outcome.
  5. في نهاية الشهر يُبنى شيت تحويل المعلمين تلقائياً، ثم تعتمد الإدارة التحويل يدوياً، وتتحول الحالات إلى paid دون كسر السجل المالي.
  6. النظام يخرج ملخص Revenue Remainder بعد خصم مستحقات المعلمين والاستردادات مع أثر واضح في التقارير.
  7. الحصص المخصصة للأطفال يمكن أن تفعل مؤثرات التشجيع، بينما حصص الكبار تبقى بدونها، ضمن نفس Room OS والسياسات.

19) المطلوب من المبرمج بلا التباس

  1. ابنِ Madar كنظام domains مترابطة، لا كمجموعة صفحات HTML.
  2. ابدأ بتعريف entities وstate machines وpolicies قبل أي تجميل واجهات.
  3. نفّذ closed loop كاملة: booking → payment → room → archive → payable → payout review → monthly settlement.
  4. عامل Room OS كقلب تنفيذي من المنظومة لا كملحق ثانوي.
  5. اجعل ledger هو مصدر الحقيقة المالية الوحيد.
  6. أبقِ تحويل مرتبات المعلمين معتمداً يدوياً في هذه المرحلة عبر payout sheet approval، مع تصميم يسمح لاحقاً بالأتمتة بضغطة زر.
  7. اكتب test scenarios end-to-end تغطي الطالب والمعلم والإدارة والوسائط والمال.
  8. لا تعتبر المشروع ناجحاً إذا غاب أي رابط بين الجلسة والأرشيف أو بين completion والمستحقات أو بين التحصيل والإقفال المالي.
